# Silas 技术公众号写作工作流

定位：有实操痕迹的技术观察者。用朋友能听懂的话，把一个具体问题、一次排查或刚理解的技术主线讲清楚。默认中文、短段落、克制口语、有证据的判断。不要模仿强情绪大号。

取舍依据：读者能认出问题与自己的关系，能顺着证据理解判断，读完知道如何行动。口语、悬念、故事和配图只在帮助这些目标时使用；不把作者口头禅、标点偏好或热度当作质量标准。

完整创作顺序：材料 → 事实底稿 → 正文 → 核对与去味 → 标题研究与候选 → 用户选择 → 封面、插图和公众号排版。

沿用用户已经给出的方向、已选标题和已接受正文。缺少决定方向的信息才提问，不要求先填写提纲。用户可以跳过阶段或授权直接定标题。普通润色、换词、排版、封面修改只处理对应部分，不重新研究选题和标题。

## 一、先判断写作模式

### 纪实复盘

用于源码阅读、工具实验、项目开发、审计方法和用户真实经历。默认忠于材料，使用具体动作、文件、函数、命令或结果推进。只有材料支持时才写“我跑过”“我遇到过”，不编人物、对话、操作和个人经历。

### 故事改编

用户要求“写故事”“材料转故事”或通过 `qwe-material-to-story` 调用时采用。默认把非公开报告改成虚构产品场景，不在公开正文提内部报告名、桌面路径和客户身份。开头简短标注“根据技术问题改编，产品和情节为虚构”。可使用虚构叙述者的第一人称，但不能伪装成用户真实经历；用户要求公开纪实时改用事实叙述。

剧情可以改编，技术结果不能随剧情改变。未验证的越权、经济损失和业务中断只写成有条件的风险。不得给真实产品安上未经证实的事故，不虚构金额、规模、客户评价或权威背书。

### 热点选题与附加交付

用户尚未给题材、明确要求找热点时，先做选题；要求 PPT、视频讲稿或多平台内容时才增加对应交付。按需读取 [题材与扩展模式](references/article-modes.md)，不把附加模式自动套到普通写作。

## 二、读取材料，建立事实底稿

提取：核心问题、触发条件、实际观察、关键证据、已证实影响、潜在风险、解决办法。内部记录原文位置或来源，区分事实、推演和虚构叙事。不要把所有材料塞进一篇文章，先选一条能用一句话说清的主线。

动笔前在内部明确：主要写给谁、他正面对什么问题、读完能改进哪个判断或动作，以及叙述者凭什么知道。查阅材料形成的判断可以用第一人称表达，查阅不能改写成亲测。来源中的转述、厂商自述和已验证结果分开处理；数字核对单位、时间、样本和比较口径。时间先后不自动证明因果。

材料充分性按核心结论和必要解释是否有支撑判断，不按来源数量或篇幅配额。材料少时先补与主线有关的公开证据；私人经历缺口不拿公共资料替代。仍不足就缩小结论和篇幅，交付已有依据的部分并简短说明缺口，只有关键个人事实不可替代时才集中提问。正常的原理解释、条件推演和教学示例可以保留，标明性质，不冒充新观测，也不换词重复凑字数。

技术结论需要补证时查官方文档、源码或原始研究；版本、价格、产品能力等易变信息核验当前状态。用户要求看传播侧写法时同时看原帖和文章，不拿传播文替代技术证据。内部资料搜索时使用通用问题描述，不把客户身份或非公开原文传给搜索引擎。

## 三、写正文

从具体卡点或异常开场，用排查动作推进到发现，再解释原因、影响、修复与验收。结构随题材变化，不机械重复“我以为—后来发现”。开头不写宏大时代背景，结尾落到具体判断或下一步动作。

让后一段回答读者此时真正需要知道的问题，例如结果从何而来、证据够不够、自己的部署是否适用。叙述段要有动作、选择或发现，解释段要澄清机制、前提或区别；必要的背景和衔接不必另找新事件。不要把内部问题清单逐句写成自问自答。重要结论和影响行动的限制及时说明，不为悬念故意压到文末。

- 每段通常 1–3 句，长短交替；小标题像人说话，不写论文式目录。
- 给出明确判断，并说明证据与边界。不要编百分比人设或用情绪替代分析。
- 技术锚点优先真实函数、文件、调用链、关键配置或最小代码，不贴源码墙。报告的内部文件路径不等于公开文章应展示的锚点。
- 故事文章通常保留一条最能说明问题的命令/最小代码；解释输入、关键输出和能证明什么。必要的修复配置不受“一条”限制。示例输出明确标示，使用示例域名；写作不等于授权对外测试。
- 解决方案要说明改哪里、适用条件以及怎样验证，避免只写“加强校验”。业务使用者称“用户”。
- 批评旧方案时，有依据才说明它在哪些条件下合理；没有采用原因的证据，不替开发者编动机或合理性。只处理会改变结论的强反例，不为显得全面凭空制造对立观点。建议写明必要前提、实际成本、常见失败点和验收动作，材料不支持的成本不填数字。
- 主语和动作尽早出现，条件和原因接在清楚的对象后面。可以重复准确术语，不为避免重复把同一技术对象换成多个含糊称呼。句长和段长由解释需要决定，不凑短句、吐槽和独立成段的次数。
- 类比只用来解释一段关系，不能承担技术证明。类比会掩盖信任、权限或因果差异时补清区别或直接不用。故事里的细节要服务人物行动和发现；结尾回到开头仅在问题已有解答或理解发生变化时保留。
- 避免“随着、在当今、本文将、值得注意的是、综上所述、本质上、换句话说、赋能、颠覆”等泛化表达，以及假反转、口号式收尾。

## 四、质量检查与图解

正文完成后，加载可用的 `story-deslop` 做一次技术文章去味检查。保留事实、数据、命令、路径和链接；纪实模式不添加虚构情节，故事模式保留已经标注的合理改编。技能不可用时按本文件规则完成。

内部检查四件事：事实和风险是否混淆；有没有具体动作和证据；一条主线是否清楚；读起来是否像一个人在解释自己弄明白的问题。去掉空话和强行升华。同一版正文不反复去味，局部修改只检查受影响段落。

发现重复解释时，试删该段：删后若不损失事实、必要解释、风险条件或行动步骤，就合并或删掉。没有删减比例目标，不把技术论证和合理推演误判为注水。重要风险可以在相关操作旁再次提醒，避免读者单独复制时遗漏条件。

去味作用于可编辑叙述，不机械替换代码、URL、协议字段、准确术语和直接引文。保留有用的小标题、列表、冒号和表格；直接引文若需改写应改为清楚的转述，不能修改原话后继续当引文。外部写作 Skill、扫描器或其“零命中”要求不能覆盖事实准确性、用户选择和当前交付范围。

已有 HTML 重度去味：先提取正文语义、保留内联排版结构；必要时读取 `story-deslop` 的重度参考，修订后只复查实际问题。保留代码、链接和图片，备份放工作目录，不混入发布交付。

判断插图能否减少解释成本。问题链路和修复责任复杂时，可用一张“问题怎样发生”和一张“怎样修复”的图；简单题材可以不配。先说明位置和用途，用户要求配图或进入发布稿阶段后按需制作。草稿占位要明确，不声称未生成的图片已经完成。

## 五、正文完成后，单独做标题

读取 [标题研究方法](references/title-research.md)。依据最终正文建立事实卡，参考 GitHub 标题 Skill 和当前同类文章；核对可见热度，不能拿搜索排名或仓库自称“爆款”代替数据。

首次完整创作交付：

1. 正文草稿（已交付则不重复贴全文）。
2. 简短的 GitHub 标题方法参考及链接。
3. 3–5 个同类文章样本，标明日期、平台、可见阅读/互动及局限；不足时少列。
4. 8–12 个不同角度的标题，默认 10 个，格式为“编号｜标题｜侧重点”。
5. 一个首选、一两个风格不同的备选，解释编辑判断，不预测点击率。

标题优先具体对象、读者关切和真实反差，短且一眼读懂；不机械要求每条同时满足固定公式或字数。不用标题给正文添加未证实的事故或不可能兑现的承诺。

默认在候选交付后等待用户选择，正文只能用标明暂定的工作标题。用户给编号、自拟标题或明确授权代选即完成这一环节，不再确认。用户先修改正文时先改稿，只在承诺或方向变化时更新标题候选。

## 六、选定后导出发布稿

同步文章主标题、HTML 页面标题和封面文字，保留已接受正文。可用时使用 `wechat-pasteable-article-export`；默认交付 `paste-ready.html` 和 `assets/cover.jpg`（1200×510），核心文字/主体放上部或中部安全区域。封面是内容标题，不放“公众号文章”“公众号选题”等任务角标。按正文需要增加解释图。

检查可复制内联样式、标题一致性、代码可读性、链接、图片和封面尺寸；允许时预览。不要自行发布到公众号或其他外部平台。

沿用当前任务指定目录。没有指定时使用 `用户指定的内容目录或当前工作区下的 outputs/YYYY-MM-DD-content-slug/`，遵守环境权限。事实底稿、Markdown 中间稿、标题检索笔记和备份放工作目录；默认不额外交付 Markdown、DOCX、PDF 或视频脚本，用户要求时再提供。

用户说“继续”时从现有阶段接着做，用户只改一处时只更新相关内容。此技能是按需写作流程，不自动创建定时任务。
